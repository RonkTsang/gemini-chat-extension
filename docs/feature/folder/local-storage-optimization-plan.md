# Folder 本地存储：产品与技术优化清单

整理日期：2026-10-06。

本文件记录本次讨论的结论及待执行事项。当前代码仍保留可选存储授权和 low 提醒流程；以下优化尚未整体实施。

## 1. 产品目标与数据边界

用户首先关心当前整理是否保存，其次关心误操作后能否恢复，最后才是异常发生时如何处理。

| 数据 | 用户价值 | 保存失败的影响 |
| --- | --- | --- |
| 当前 Folder 整理 | 文件夹、对话归属、顺序等修改在下次打开时仍然存在 | 本次修改没有保存成功，必须明确反馈 |
| 恢复历史 | 回到之前的整理版本 | 最新版本没有恢复点；已有恢复点仍可使用，除非另有读取失败 |

恢复点只保存在本设备，并按 Gemini 账号隔离。恢复只改变 Folder 整理，不改变 Gemini 对话本身。

已采用的恢复策略继续保留：每个账号最多 10 个恢复点、不按时间过期、相邻自动变化分组并去重、跨账号共用 20 MiB 产品预算。系统自动清理可移除的旧历史，并保留正在参与操作的保护恢复点。

## 2. 权限与容量结论

- Chrome 的 `unlimitedStorage` 不能作为可选权限。采用该权限时，应在 `permissions` 中默认声明，不提供运行时“申请更多空间”流程。
- 该权限免除通常的扩展源存储配额限制，不表示物理磁盘无限，也不保证每次写入都成功。
- 每账号 10 个恢复点与跨账号 20 MiB 预算是产品自身的限制，与浏览器配额不同。
- `navigator.storage.estimate()` 可用于开发诊断；具备该权限后，不应仅凭它的剩余比例阻止保存或生成面向用户的 low 警告。
- Firefox 的权限声明方式及行为需要独立核实，再决定是否统一默认授权。不能据 Chrome 的规则直接删除 Firefox 仍可能使用的共用流程。

依据：[Chromium 权限定义](https://github.com/chromium/chromium/blob/main/extensions/common/permissions/extensions_api_permissions.cc)、[Chrome 扩展存储说明](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies#persistence)。

## 3. 用户状态与反馈

### 三种主要状态

| 状态 | 文案与呈现 | 有效操作 |
| --- | --- | --- |
| 正常 | 保持安静，展示恢复点数量、最后成功保存时间 | 查看历史、创建恢复点、导入／导出 |
| 最新恢复点未保存 | 黄色；在确认当前整理已保存时显示“整理已保存，但最新恢复点未能保存。” | 临时失败可重试；当前版本过大时提供导出备份及说明 |
| 当前修改未保存 | 红色；在对应操作附近显示“这次更改未保存。” | 具备可重试条件时重试；撤回未经确认的成功状态 |

“当前整理已保存”必须由真实写入结果确认。手动创建恢复点失败时，不应凭空宣称刚才有一项整理修改已保存；可直接显示“恢复点未能创建”。

### 操作前保护失败

删除、导入、恢复前需要成功创建保护恢复点。失败时阻止本次操作，并在对应操作中说明：

> 无法保存操作前的恢复点，本次操作未执行。

这是具体操作的失败反馈，不需要在 Recovery 中增加一个长期的用户状态。

### 呈现与交互规则

- 正常达到数量／预算上限，自动清理后保存成功，不显示容量警告。
- 最近保存时间始终指向最后成功创建或更新的恢复点；失败不更新该时间。
- Info 保留本设备、账号范围、恢复内容、最多 10 个、自动替换旧历史等用户规则。
- 本地容量比例、字节数、额度估算、权限状态移至开发诊断，不作为正常界面的主要信息。
- 移除 Chrome 的“允许更多存储”、对应授权步骤及相关引导文案。
- 移除未经确认的“释放磁盘空间”建议。实际写入失败不能直接等同于磁盘已满。
- 导出备份用于保护当前整理，不释放空间、不代替旧恢复点、不解决存储写入失败本身。
- 错误明确说明哪项工作未完成，避免同一次失败在区块、确认框和 Toast 中重复提示。
- 保留明确的操作结果，例如“恢复点已创建”“备份已导出”。

本次检查发现上述授权流程仍存在于 `wxt.config.ts`、`RecoverySection.tsx`、`LocalStorageDetails.tsx`、`openStoragePermissionPage` RPC 和 `folder-storage.html`，不能只改按钮文案。

任何本地化修改继续使用项目规定的 i18n 子代理。保留现有未提交工作，不将其他 Folder／账号／反馈通道改动纳入本轮重构。

## 5. Debug 调整

- 保留仅开发环境可见、生产包排除 Debug 模块的边界。
- 保留真实存储测量用于诊断，但明确 `estimate()` 不是具备权限后的可用容量硬上限。
- Chrome 移除“容量不足可申请权限”“容量不足已授权”的模拟场景。
- 增加／保留：正常、自动清理后保存成功、单个恢复点过大、临时恢复点失败、保护点暂时无法清理、当前整理保存失败、操作前保护失败。
- 不仅预览黄色恢复警告，也覆盖红色当前保存失败和操作确认框中的保护失败。
- 模拟状态与真实数据明确分开；预览操作不删除真实恢复点、不更改权限、不触发真实导入／恢复。
- 本轮不调整已确定的 Browser Sync 容量百分比、颜色及说明设计。

## 6. 验收清单

- [ ] Chrome 生成 Manifest 的 `permissions` 包含 `unlimitedStorage`，`optional_permissions` 不包含它；真实 Chrome 确认权限有效。
- [ ] Firefox 声明符合独立核实的能力，两个构建均成功。
- [ ] 普通界面没有无效授权按钮、授权流程和仅凭估算产生的 low 警告。
- [ ] 达到 10 个／接近 20 MiB 时，自动清理成功即视为正常；当前整理不受清理影响。
- [ ] 自动恢复点失败，但当前事务成功时，明确区分保存成功与恢复历史未更新。
- [ ] 单个恢复点过大时，不展示没有意义的无限重试，也不承诺删除历史即可解决。
- [ ] 保护点暂时不可清理时，不误报单个恢复点过大，不删除正在使用的保护点。
- [ ] 当前整理事务失败时，不显示保存成功；界面与实际持久化结果一致。
- [ ] 删除、导入、恢复前保护失败时，本次操作未执行。
- [ ] 恢复成功后状态清除；失败时保留最后成功时间；账号切换无过期反馈串入。
- [ ] 失败状态记录也写入失败时，原始失败仍能抵达 UI。
- [ ] Debug 可查看对应状态，按钮不产生真实数据副作用；生产产物不包含预览模块。
- [ ] 类型、相关存储／事务／UI 测试与翻译一致性检查通过，并验证真实 Chrome 边界，而非只依赖模拟 API。

## 7. 单独待评估事项

每条恢复点的删除能力尚未确定实施。它应作为历史管理功能评估，而非所有容量错误的统一解决方案。如加入，需要账号校验、正在使用的保护点限制，以及明确“删除的是历史版本，当前整理不变”的确认反馈。

推荐执行顺序：权限修正与平台决策 → 保存结果和错误原因区分 → 用户界面与翻译 → Debug 场景 → 自动测试、生成产物和浏览器验证。
