# Theme Bloom 排障指引

本文用于定位真实 Gemini 页面上的 Theme Bloom 拖放与首帧动效问题。它不是功能已验证或已修复的声明：**扩展刚安装后的首次拖放异常仍未解决**；目前只确认页面刷新后的首次拖放表现已改善。

## 边界与原则

- Gemini 原生图片上传区必须始终 fail open：不拦截、不 `preventDefault()`，也不触发 Theme Bloom。当前需在真实页面确认 `input-area-v2` 内 `rich-textarea > .ql-editor[contenteditable="true"][role="textbox"]` 及其实际事件路径。
- 不保留常驻日志或以单次自动化测试替代真实浏览器证据。日志只用于缩小尚不确定的边界，并在同一 PR 删除。
- 不先改动坐标、动画或选择器来“试修”。先取得能区分事件采样、跨脚本交接、Shadow DOM 布局和 View Transition 的证据。

## 复现矩阵

对每种场景均使用同一张本地 PNG/JPEG/WebP，分别拖到非输入区和 Gemini 原生上传区；每次只测一次“首拖”，再测一次“第二拖”。记录扩展版本、Chrome 版本、页面 URL/会话类型、窗口尺寸与缩放比例。

| 场景 | 准备 | 重点观察 |
| --- | --- | --- |
| 新装扩展后的首拖 | 已打开 Gemini 页面时安装/重新加载扩展；不要刷新页面 | 首次非输入区拖放的落点、圆形起点、换肤和原生上传避让 |
| 页面刷新后的首拖 | 在相同页面刷新后，等待页面稳定，再拖放 | 与新装路径的首帧、坐标、primer 状态逐项比较 |
| 后续拖放 | 在同一页面完成首拖后再次拖放 | 判断是否仅首帧问题，避免把稳定后的结果当成首拖证据 |

安装注入、页面刷新和运行中启用是不同生命周期；不要用刷新路径的成功推断安装路径也已修复。

## 证据优先的诊断顺序

按下列顺序推进；前一层证据不足时，不进入下一层。

1. **事件路由与目标。** 在真实拖放目标上确认 `event.target`、`composedPath()`、文件类型与是否进入原生上传区。若目标或路径命中原生上传区，应观察到完全放行。
2. **捕获落点。** 确认拦截层选择的 `clientX/clientY` 与用户实际松手处一致；只有需要跨层临时对照时，才为该次拖放分配一次性会话 ID。
3. **Shadow DOM 几何。** 确认覆盖层收到同一会话、种子元素的 `getBoundingClientRect()` 中心与预期落点一致；同时记录包含块、滚动位置、视口尺寸和缩放。
4. **View Transition。** 仅在前三层正确时，检查 transition 使用的坐标空间、`::view-transition-new(root)` 的圆心、primer 是否在可见且页面稳定后完成，以及降级路径是否正确应用主题。

如需临时插桩，建议按会话 ID 串联 `arbiter:drop-intercept`、`channel:publish`、`overlay:state-received`、`overlay:layout` 与 `transition:coordinates-committed`。这些名称是排查时的对照点，不构成应永久保留的埋点清单。

## 症状与可能层级

| 症状 | 优先怀疑的层级 | 下一步 |
| --- | --- | --- |
| 原生上传区被换肤或上传失效 | 事件路由/目标分类 | 保存 `target` 与完整 `composedPath()`，先恢复 fail-open 边界 |
| 非输入区未触发，或只有第二拖有效 | 捕获或跨脚本交接 | 对比首拖与第二拖的拦截、发布、接收顺序 |
| `chosenOrigin` 已正确，种子却出现在别处 | Shadow DOM 布局 | 比较预期落点与实际 `getBoundingClientRect()` 中心、包含块和滚动 |
| 覆盖层位置正确，圆形揭示从错误位置开始 | View Transition | 核对 transition 圆心和伪元素所用的视口坐标空间 |
| 新装首拖异常、刷新后首拖正常 | 安装生命周期 / primer | 记录可见性、页面稳定时机和 primer 各完成阶段；这只是待验证假设，不是已确认根因 |
| 动画失败但主题已切换 | Transition 降级 | 检查降级动画；主题应用不得依赖动效成功 |

## 临时 DEV 插桩规则

只有在上述证据无法判断的**单一边界**添加最小 DEV-only 插桩：例如仅记录一次 `composedPath()`，或仅记录一次覆盖层几何，或仅记录 primer 的完成顺序。每条记录应包含会话 ID、时间、输入与输出；不得记录图片内容、用户提示词或无关页面数据。

插桩 PR 必须同时做到：

1. 写明待证伪的问题与唯一插桩边界。
2. 提供首拖与第二拖的对照证据。
3. 得出结论后在**同一 PR**移除插桩；不能以“以后可能有用”为由保留常驻日志。

若结论仍不确定，保留问题与复现材料，不扩大日志覆盖面或宣称已修复。

## 最低交付证据

- 新装扩展首拖、刷新后首拖、第二拖的真实浏览器截图或视频；画面应同时能辨认拖放落点、动画起点及最终主题。
- 原生上传区拖放的截图或视频，证明其仍交给 Gemini。
- 每份材料附精确设置：扩展构建/提交、Chrome 版本、Gemini URL 与会话类型、安装或刷新步骤、等待时长、窗口尺寸、设备像素比/浏览器缩放、测试图片格式与尺寸、是否 reduced motion。
- 如使用临时插桩，附同一会话 ID 的最小日志片段及其对应视频时间点。

仅通过单元测试、合成 `window` 事件或 `git diff --check`，不能证明真实首拖路径、Shadow DOM 首帧几何或 View Transition 坐标正确。
